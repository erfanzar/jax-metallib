## What this project is

jax-metallib is a native PJRT (Pluggable Device Runtime) plugin that lets JAX execute on Apple Metal GPUs by compiling StableHLO IR to Metal compute kernels via MPSGraph. It is a dual-language project: Python (plugin registration, custom kernel API, quantization) + C++17/Obj-C++17 (PJRT C API, MPS backend, op lowering, Metal runtime).

- **120 StableHLO ops** registered across 15 op category files
- **3 execution paths**: MPSGraph compilation, native Metal kernels for perf-critical ops, JIT fusion of elementwise chains into custom MSL kernels
- **Platform**: macOS 15.0+ (deployment target; 13.0 builds had 272 unguarded newer-API uses), Apple Silicon only
- **JAX version**: 0.11.x

## Architecture & runtime flow

**4-tier stack:**
1. **Python** (`src/jax_plugins/silicon/`) — plugin registration, custom Metal API, quantization
2. **PJRT C API** (`src/pjrt_plugin/api/`) — standard XLA plugin interface vtable
3. **Core MPS Backend** (`src/pjrt_plugin/core/`) — `MpsClient`, `MpsDevice`, `MpsBuffer`, `MpsExecutable`
4. **Ops + Runtime** (`src/pjrt_plugin/ops/`, `runtime/`) — 120 registered handlers, native Metal kernels

**Execution flow:**
1. JAX compiles Python to StableHLO IR (MLIR bytecode)
2. `MpsExecutable` parses the module via `stablehlo_parser`
3. `BuildExecutionPlan()` walks ops, classifies into `GraphStep` (MPSGraph) or `NativeStep` (Metal kernel)
4. Fusion passes merge elementwise chains, LayerNorm, Softmax, ReduceMean into fused native kernels
5. `Execute()` binds input buffers, runs graph segments via `MPSGraphExecutable`, native segments via `MTLComputeCommandEncoder`, and returns `CompletionEvent`

**Dual-path dispatch:**
- **GRAPH** handlers build `MPSGraphTensor` DAGs via `registry.h` macros
- **NATIVE** handlers bypass MPSGraph and directly encode Metal compute kernels for performance-critical ops (Cholesky, triangular solve, softmax, LayerNorm, GEMM, sort)

## Agent workflow rules

1. **C++ changes require rebuild**: Any edit to `.mm`, `.cc`, or `.h` in `src/pjrt_plugin/` requires `uv pip install -e .` before testing.
2. **Clear caches after C++ changes**: Delete `~/.cache/jax-silicon/autotune_cache.bin` and `~/.cache/jax-metallib/autotune_cache.bin` after changes that affect GEMM or elementwise kernels. The autotune cache is unversioned binary and can pick stale variant decisions.
3. **Use `JAX_TEST_MODE=mps` for fast iteration**: The default `compare` mode runs every test on both CPU and MPS. For quick feedback, use `JAX_TEST_MODE=mps`.
4. **Avoid eager gradients in compare mode**: `test_op_grad` is skipped in `compare` mode because eager gradients deadlock the Metal command queue after many prior dispatches. JIT gradients are the tested path.
5. **No pre-commit hooks**: Despite `CONTRIBUTING.md` claiming pre-commit hooks, there is no `.pre-commit-config.yaml`. Run formatting and tests manually.
6. **Subprocess benchmarking**: `vs_jax_mps.py` and `vs_cpu.py` spawn separate Python processes because `jax-mps` and `jax-metallib` both register as `mps` platform and cannot coexist in one process.
7. **Platform guard**: This only works on macOS Apple Silicon. Non-Darwin platforms raise `SiliconPluginError`.
8. **Shardy disabled**: The plugin auto-sets `jax_use_shardy_partitioner = False` because the StableHLO parser does not support `sdy` dialect ops.

## Project-specific caveats

- **mps_executable.mm is ~9.7K lines**: This is the heart of the backend. Changes here affect execution plan building, dispatch, native kernel baking, and memory management. Read carefully before editing.
- **Per-op dispatch overhead ~250–550 µs**: Small tensors (<10K elements) are often faster on CPU. The GPU wins at scale (matmul >4K×5K, sort >100K, conv >1K channels).
- **Exponential first-call cost on some unrolled reconvergent chains** (MPSGraph, not fixable from an op handler): a Python-unrolled elementwise recurrence whose carried value feeds two ops that rejoin every step can make the first execution grow ~2x per step, while steady state stays ~1-3 ms. A stack sample (`build/sample_rot_r19x.txt`) puts the time in `MpsExecutable::BuildExecutionPlan` -> `-[MPSGraph compileWithDevice:...]` -> `MPSGraphExecutable cloneForFeeds:` -> `getOperationsToVisitForOperation:visitedOperations:`, i.e. MPSGraph's lazy executable build, not constant folding or Metal shader compile. Measured first calls at 2^16 (`build/probe_traversal*_r19x.log`, `probe_realistic_r19x.log`, `probe_scalar_feed_r19x.log`; load 5-11, so absolute times are inflated): 1-word rotate `rotl(v) + c` N=14/16/18/20 0.09/0.24/0.71/2.6 s; `v*3 + v*5 + c` N=16/18/20 1.5/6.1/30.5 s; logistic `3.7*v*(1-v)` N=16/18/20 0.19/0.67/2.7 s. Not affected (~0.02 s at N=20): ThreeFry's two-word round (so `jax.random` is fine), Newton `y*(2-x*y)`, `x + 0.1*sin(x)`, and straight chains (`v*x + c` N=80 2.3 s, roughly linear). Falsified explanations, do not retry: op count, the shift `|` pattern (`+` blows up the same), a reused runtime argument, the uint32->int32 bitcast cut, and the scalar-constant feed (constants passed as full-size runtime arrays still grow at the same rate; `JAX_METALLIB_DISABLE_SCALAR_OPERAND_BROADCAST=1` changes nothing). Workarounds: use `lax.fori_loop`/`scan` instead of a Python loop (measured, `build/probe_loop_workaround_r19x.log`: logistic unrolled N=20 2.6 s vs fori 0.04-0.14 s / scan 0.013 s, dia unrolled N=20 4.4 s vs fori 0.05 s / scan 0.017 s; both flat up to N=40 and bitwise equal to the unrolled result), or keep unrolled reconvergent chains short (<= ~14 steps). A planner-level fix (splitting the graph before `compileWithDevice` in `mps_executable.mm`) is deferred.
- **macOS 15.0 is the minimum**: `CMAKE_OSX_DEPLOYMENT_TARGET` must be set before `project()` in CMakeLists.txt. Set after it, as it used to be, the setting was ignored and the dylib declared `minos` = the host OS (27.0), so a wheel would only load on the build machine's macOS. A 13.0 target warned on 272 unguarded APIs (13.1-15.0: reinterpretCastTensor, bf16, FFT, complex parts, sliceUpdateDataTensor, reciprocalSquareRoot) with no runtime fallbacks; 15.0 builds with 0 such warnings (`build/build_r20j_deploy_target{,15}.log`).
- **Mixed-precision GEMM is opt-in**: fp32 matmuls stay fp32 by default. `JAX_METALLIB_GEMM_FAST_F32=1` restores the fp16 input cast for large DEFAULT-precision dots (overflows above 65504).
- **Native intrinsic kernels are disabled by default on JAX 0.11** (`JAX_METALLIB_ENABLE_INTRINSIC_NATIVE_KERNELS=1` to opt in): eager dispatch exposed a `CFRelease(nil)` abort on eliminated output slots (fixed in 0.11.1.0) and fused-chain scheduling defects — the broadcast-ordering wrong-results bug is fixed (chains now split at externally-consumed intermediates), but a slot-aliasing defect remains for some MultivariateNormal log-prob gradients under the opt-in flag. `test_native_intrinsic_ordering_bug` guards the ordering pattern.
- **Bumping JAX**: pins come from the JAX release's `MODULE.bazel` `archive_override` (XLA commit), XLA's `third_party/stablehlo/workspace.bzl` (StableHLO commit), and that StableHLO commit's `build_tools/llvm_version.txt` (LLVM commit). After changing pins, `setup_deps.sh --force` is mandatory — stale installed headers shadow fresh builds.
- **Metal has no `atomic_half`**: Scatter-add uses non-atomic read-add-write; duplicate indices may lose updates.
- **Convolution dtypes** (`convolution_ops.mm`): MPSGraph convolution accepts only FP32/FP16 and aborted the process on integer operands. 1-D/2-D integer convs (int8/16/32, uint8/16/32, incl. `preferred_element_type=int32`, strides, lhs/rhs dilation, negative padding, feature groups) are now lowered exactly in int32 per kernel tap (wraps modulo 2**32 like XLA:CPU; slower than the float conv). 3-D integer convs and integer `batch_group_count > 1` return an error instead of aborting. f16/bf16 convs with `preferred_element_type=float32` widen the operands to f32 (previously the f16 result bytes were read as f32: errors up to 2.9e6, no error raised); every conv result is cast to its declared dtype. Regressions: `tests/test_conv_dtypes.py`.
- **Declared result dtype is not enforced by `Result()`** (`registry.h`): a handler whose MPSGraph output dtype differs from the op's declared element type has its bytes reinterpreted, with no error. bf16 x bf16 `dot`/`dot_general`/`einsum` with `preferred_element_type=float32` hit this (relative error ~1.0-1.5); bf16 operands are now widened to f32 (exact) after the fp32->fp16 mixed-precision block, and `HandleDotGeneral` casts float results to the declared type as a backstop. f16 and integer contractions, and bf16/f16/int `sum`/`cumsum`/`mean` with a wider dtype, were probed and already matched CPU. Regressions: `tests/test_dot_preferred_dtype.py`.
- **Handlers JAX never emits are run by `tests/test_unemitted_ops.py`**: `stablehlo.broadcast`, `dot`, `map`, `dynamic_broadcast_in_dim`, `dynamic_reshape`, `get_dimension_size` and `set_dimension_size` are listed as exercised in the `tests/configs/util.py` HACK set, so the CI coverage check never ran them. The test emits each through a custom primitive and compares MPS with XLA:CPU bitwise, one child process per case (17 cases). That uncovered a crash: a matrix-vector `stablehlo.dot` (`[M,K]·[K]`, also `[K]·[K,N]`) aborted the process with the MPS assertion `K dimension is inconsistently defined` (rc=-6). `binary_ops.mm` `HandleDot` now promotes the vector operand to `[K,1]`/`[1,K]` and reshapes the product to the declared result shape on the float, f16-widened and integer paths. vector·vector and matrix·matrix were already exact and are unchanged.
- **Width-changing `bitcast_convert` left the wrong graph shape** (`shape_ops.mm` `HandleBitcastConvert`): `reinterpretCastTensor` scales the last dimension (u16[6,4,2] -> u32 gave 6x4x1, u32[6,4] -> u16 gave 6x8), while StableHLO drops or appends that axis (6x4, 6x4x2). A bare bitcast still returned the right bytes, but any consumer saw the wrong rank. `add`, `shift_left`, `multiply` and `reverse` on the result aborted the process inside MPSGraph (SIGABRT, e.g. `'mps.add' op requires the same element type`, `'mps.reverse' op invalid axis: 2`). u16[8,2] -> u32 followed by `+ 1` broadcast [8,1] + [8] to [8,8] and returned 7/8 wrong values. Before the fix, `build/probe_r20h_bitcast_shape.log` had 8 aborts and 1 wrong-value case out of 17; after it, `probe_r20h_bitcast_shape_fix.log` has 0 aborts. The handler now reshapes to the declared static result shape; the bytes are already in order, so no data moves. Same-width bitcasts are unchanged. Found while emulating a pair-packed f16 reverse (u16 pairs -> u32), which turned out 1.29-1.50x slower than the current reverse and was dropped (`build/probe_r20h_reverse16_fix.log`). Regressions: `tests/test_bitcast_width_change.py` (21 cases, one child process each, bitwise vs XLA:CPU).
- **Reducer and scatter bodies are matched strictly**: `reduce`/`reduce_window` accept only a single binary op on the block arguments (the reducer used to be named after the body's first op, so `lax.cumlogsumexp` ran as cummax); a logaddexp body is supported only as a full cumulative scan (`lax.cumlogsumexp`, exact associative scan). Scatter accepts set/add/mul/min/max (and the sub/div forms JAX emits, bool or/and); any other update computation such as `x.at[i].apply(f)` raises `scatter: unsupported update computation` instead of silently writing the updates. Gather clamps start indices like StableHLO (`take(mode="clip")` returned zeros before). Regressions: `tests/test_gather_clamp_scan_scatter_body.py`.
- **Batched and windowed gather/scatter fallback** (`shape_ops.mm` `GatherExplicitCoordinates` / `ScatterExplicitCoordinates`): gathers and scatters that no specialised path accepts, notably `vmap(lax.dynamic_slice)` / `vmap(lax.dynamic_update_slice)` (operand_batching_dims with a multi-component index vector, and their gradients), used to raise `unsupported gather/scatter pattern`. They now evaluate the StableHLO definition directly: each element's operand coordinate (clamped start for gather, plus batching iota, plus window offset) is stacked per dimension and passed to gatherND/scatterND on the unflattened operand (bool is widened to uint8 because scatterND drops bool updates). A flat 1-D gather/scatter of linear indices was measured first and was slower: vmap ds 256x[256,256]->32x32 1.33 -> 0.65 ms, vmap dus 256x[256,256]<-32x32 4.31 -> 1.48 ms (the flat scatter copied the input twice for its dummy slot). The fallback runs only at the former error sites and the batched-scatter rank guard, so existing fast paths are unchanged. A windowed scatter in `mode="drop"` whose window only partly fits used to be partially written (scatterND drops out-of-bounds elements one at a time); XLA skips the whole window, and windows wider than 1 on a scattered dim now route to the explicit lowering, which gives every element of a non-fitting window an out-of-bounds row coordinate so scatterND drops the whole window (verified with starts of -1000 and 2**30). Overlapping `set` windows may differ from CPU, because XLA leaves their write order unspecified. Static shapes below 2**31 elements only. Regressions: `tests/test_vmap_dynamic_slice_scatter.py`.
- **Cumulative and sliding max/min propagate NaN** (`reduction_ops.mm` `HandleReduceWindowImpl`): MPSGraph `cumulativeMaximum`/`cumulativeMinimum` skip NaN, so `lax.cummax([3, nan, 5])` returned `[3, 3, 5]` (f32, f16 and bf16, both scan directions) where XLA propagates NaN from its position onward. A cumulative max over an `isNaN` flag now puts NaN back; the sliding fold and the final init fold use the NaN-propagating max/min for float types (plain max/min replaced a propagated NaN with the ±inf init). The sliding max/min/multiply path also accepts bf16 now (it rejected it with "requires a float window <= 32"). bool `reduce_window` with max/min/or/and raised `unsupported pattern`; a wrapper runs it on the exact 0/1 uint8 widening (or as max, and as min) and maps back with `!= 0`. Regressions: `tests/test_cumulative_nan_bool_window.py`.
- **TOTALORDER compares** (`binary_ops.mm` `HandleCompare` / `TotalOrderKey`): `stablehlo.compare` ignored `compare_type`, so `TOTALORDER` compares (JAX `lt_to`/`le_to`/`eq_to`, `jnp.searchsorted` scan/scan_unrolled/compare_all, sort comparators) used IEEE semantics: `lt_to(-0, 0)`, `lt_to(1, nan)` and `eq_to(nan, nan)` were false, and searchsorted put NaN queries past the end (MPS 6 vs CPU 4 for a NaN query into `[-1,0,0.5,2,nan,nan]`). f32/f16/bf16 operands are now compared as signed integer keys (bits reinterpreted, non-sign bits flipped for negative values), which order -NaN < -Inf < ... < -0 < +0 < ... < +Inf < +NaN like XLA. Integer and complex operands keep the plain compare. Rank-0 operands are keyed as `[1]` and reshaped back: MPSGraph's compile-time optimizer aborts (SIGABRT, no message) on `reinterpretCastTensor` of a scalar, which `jnp.digitize` on a scalar (hence `jsl.expm`) reached. Regressions: `tests/test_compare_totalorder.py` (incl. rank-0 cases).
- **Integer add of the signed minimum** (`binary_ops.mm` `HandleAdd` / `IsSignBitSplat`): MPSGraph add of a splat constant equal to `INT32_MIN` or `INT64_MIN` returned the other operand unchanged wherever the sum overflows (jit `x + jnp.int32(-2**31)` gave `-294967296` instead of `1852516352`). The same value passed as an argument, a non-splat constant, sub/mul/xor with it, and int8/int16 minimums all wrapped correctly; raw-bytes constants and `JAX_METALLIB_MPSGRAPH_OPT_LEVEL1=1` did not change it. When either operand traces (through broadcast_in_dim/reshape) to that splat, the add is lowered as `x ^ MIN`, which is exact in two's complement. Regressions: `tests/test_int_min_add_unsigned_scatter.py`.
- **Unsigned scatter reducers run in int32** (`shape_ops.mm` `HandleScatter`): 1-D `x.at[i].add/max/min/mul` on uint32/uint16/uint8 reached MPSGraph `scatterWithDataTensor` directly, which saturated adds and muls (`5 + 0xFFFFFFFF` gave `INT32_MAX`, uint16 `5 + 65535` gave 65535) and compared uint32 as signed (`max(4e9, 3)` gave 3). 2-D element scatters took the mask path and were already correct. uint32 is now reinterpreted as int32 (sign-bit XOR for min/max; rank-0 updates via `[1]`), and uint8/uint16 are widened to int32 and masked back. Regressions: `tests/test_int_min_add_unsigned_scatter.py`.
- **dynamic_update_slice / pad data loss** (`shape_ops.mm` `HandleDynamicUpdateSlice`, `HandlePad`, `ScatterNDSetExact`, `PadByConcat`, `IsConstantDerivedValue`): (1) Outside control flow, MPSGraph slice-update with constant starts returned the operand unchanged whenever the operand or update was computed in the same graph (jit `dus(a[0], b[0], (5, 9))`, `dus(x * 2, y * 3, (5, 9))`), for every dtype and every size from 8x2 to 4096x1024. The tensor-start variant fed the same constants dropped it too, because MPSGraph folds them. Starts that JAX derives from constants (`select(compare(c, 0), c + n, c)` from index normalisation) behaved the same way. Such starts now take the scatterND route. Traced starts and loop bodies were exact and keep slice-update. A full replacement (update shape == operand shape) was dropped with traced starts as well, and now returns the update directly (4096^2: 1.5-1.7 ms; the bare scatter route would have been 15.7 ms). (2) Plain scatterND (set) rounded uint32 through f32 (`1322117303 -> 1322117248`), dropped bool writes and aborted on complex (`mps_scatter_nd`, SIGABRT). `ScatterNDSetExact` scatters uint32 as int32 bits, bool as uint8 and complex as separate real/imaginary parts. The DUS fallback and interior pad both use it, which fixes uint32 interior/negative pads. (3) Edge pad: native `padTensor` materialises its double pad value through f32, which rounded or saturated integer pad values beyond 2^24 (`0xFFFFFFFD -> 0xFFFFFFFF`, `2147483645 -> INT32_MAX`), so it is now gated to f32-exact values. A traced float pad value used `(x - p)`, padded with 0, then `+ p`, which was inexact (`9053559 -> 9053558`) and gave NaN everywhere for `p = +-inf`. Both cases, and the slice-update fallback, now pad by per-axis slice/concat. That route is exact and faster: f32 4096^2 traced value 3.6-4.7 -> 1.8-1.9 ms, non-f32-exact int32 constant 4.6 -> 3.2 ms; the native constant pad is 1.6 ms. Top-level constant-start DUS through scatterND costs more than the old (wrong) path on large blocks (4096^2 <- 1024^2: 2.9-3.4 ms vs a dropped write at 1.4 ms, traced starts 2.7-3.2 ms). (4) `padTensor` also round-trips 32-bit integer **operands** through f32 when the pad value is f32-exact (0, -1, `INT32_MIN`): int32 `jnp.pad(x, 1, constant_values=-1)` returned every element above 2^24 rounded (`1638082997 -> 1638082944`, 29/32 to 1011545/1048576 elements wrong), which also broke shift-and-max scans written with `lax.pad`. The old test's pad value (`iinfo.max - 2`) is not f32-exact, so it never reached `padTensor`. int32/uint32/int64/uint64 now always take `PadByConcat` (4096^2 int32 edge pad 1.72 ms vs 1.56 ms for the f32 native pad; 1024^2 0.42 vs 0.34 ms). The integer convolution lowering (`convolution_ops.mm` `IntegerConv2DNHWC`) had the same defect in its rank-6 lhs-dilation `padTensor` (2253/2280 int32 outputs wrong for |x| > 2^24); both its dilation and edge pads now use `ZeroPadAxisExact` (broadcast zeros + concat). The rounding depends on shape and pad value (u32, i16, u8 and the conv edge pad were exact on the old build), so 32-bit integers are kept off `padTensor` entirely. Regressions: `tests/test_dus_const_pad_exact.py` (87 cases), `tests/test_int_pad_exact.py` (20 cases; 8 fail with both fixes reverted).
- **Window scatter write-back** (`shape_ops.mm` `ReinsertWindowByConcat`): a scatter whose update window is narrower than the operand on a non-scattered dim is scattered into the operand's leading window and written back. The write-back used `sliceUpdateDataTensor` with constant starts, which dropped every write whenever the operand was computed in the same graph (f32/f16/int32, set and add, 2-D and 3-D: 18/54 probe cases in `build/probe_scatter_window_update.py` returned the operand unchanged). The f32 broadcast-base workaround (`ReinsertScatterWindow`) used plain scatterND, which is not exact for uint32/bool/complex. Both are replaced by a slice/concat reassembly that is exact for every dtype and faster than the old path even where the old path was correct (argument operands, f32 4096^2 w=4095 k=64 4.25-4.33 -> 2.77-3.05 ms; w=2048 2.61 -> 1.80-2.26 ms; 1024^2 0.29 -> 0.24-0.26 ms). A full-width scatter of the same rows is still faster (1.4 ms at 4096^2) because the window slice and concat remain. Regressions: `tests/test_scatter_window_writeback.py` (99 cases incl. `jnp.zeros` bases).
- **Native max/min reductions dropped NaN** (`runtime/metal_kernels.mm` `REDUCE_MINMAX_LAST_TG`, `REDUCE_MINMAX_LAST_LIN`, `REDUCE_MINMAX_AXIS0`, `rd_nan`): the native `reduce_{max,min}_{last_*_tg,last_*_lin,axis0_*}` kernels used Metal `max`/`min` and `simd_max`/`simd_min`, which return the non-NaN operand, so `jnp.max`/`jnp.min` over >= 4096 elements (the native full-reduce route, including the single-row split + combine) returned a finite value when the input held a NaN, for f32 and f16, jit and eager (96/400 cases in `build/probe_full_reduce_nan_sweep.py`; the graph-routed partial reduces were already correct). The kernels now carry an integer NaN flag built from the bit pattern (the library is compiled with `options:nil`, i.e. default fast math, where `isnan()` may be folded) and store a quiet NaN by bit pattern. No measurable cost (f32 2^16 full max 0.355-0.359 ms before and after; 2^24 0.84-0.86 ms, same as full sum). The oracle is NumPy, not XLA:CPU: jaxlib 0.11.1's CPU backend drops NaN in the same reductions (f32 max over 4096 elements with one NaN returns `-inf`, the init value; 108/400 CPU cases wrong, unchanged by `--xla_cpu_enable_fast_min_max=false`), so CPU-compare tests cannot catch this class. The same defect was in `softmax_numerator_{f32,f16}_tg`, which the opt-in intrinsic family (`JAX_METALLIB_ENABLE_INTRINSIC_NATIVE_KERNELS=1`) uses for a bare `exp(x - max(x, axis=-1))`: a row holding one NaN returned one NaN instead of a whole NaN row (4/150 cases in `build/probe_softmax_nan.py`). Those kernels now carry the same flag and write a NaN row; full softmax kernels were already NaN-correct because the NaN reaches the row sum. Remaining gap: full reduces on the native route pay ~0.17 ms fixed per call vs jax-mps (0.36 vs 0.19 ms at 2^16); the routing lives in `mps_executable.mm`. Regressions: `tests/test_reduce_minmax_nan.py` (incl. a subprocess case for the intrinsic route).
- **Narrowing convert of constant-derived values returned the f32 bytes** (`shape_ops.mm` `FoldNarrowingConvert`, `IsCompileTimeValue`, `NarrowF32ByBits`): for a `convert` to f16/bf16 whose operand MPSGraph can constant-fold, `castTensor` produced a 16-bit tensor that still held the constant's f32 storage, and the `CastFoldBarrier` reinterpret round trip read it back. The result was the f32 bit pattern read as 16-bit values. On the default route this made f16/bf16 `jnp.clip(x, -0.5, 0.5)` return all zeros (-0.5f is `0xBF000000`, and `clip` passes its Python-float bounds into a private callee that converts them); `arange(f32) * c` (RoPE-style tables), slices, transposes, concats, gathers and pads of constants cast to bf16/f16 returned garbage (`build/probe_const_cast_barrier.py` 32/36, `probe_const_cast_sources.py` 36/48, `probe_const_cast_gaps.py` 18/30 wrong). Closed-over bf16 arrays above 4M elements also mis-rounded ties (28 of 4.2M). Eight alternative barrier forms (bitwise ops, int32 round trips, identity, `x*1`, `x+(-0)`, a reinterpret on the f32 side) failed identically, and removing the barrier lets MPSGraph fold `const -> f16 -> f32` (70000 stays 70000 instead of inf), so neither is a fix. Now: (1) constant, iota, broadcast_in_dim, reshape, convert and float add/sub/mul/div/neg chains are evaluated exactly on the host (double, rounded to the element type after each op; up to 2^22 elements) and emitted as a 16-bit constant; (2) any other f32 operand with no block argument or rng/custom_call/infeed/recv in its operand closure is narrowed in-graph by round-to-nearest-even on the int32 bit pattern (NaN as sign \| `0x7E00`/`0x7FC0`, >= 65520 -> inf, f16 subnormals), then reinterpreted, because reinterpreting a folded f32 value is exact (`probe_const_bitcast32.py` 0/18). Runtime operands keep the barrier: 0 hits on a 48-layer bf16 MLP and a bf16 scan body; timings unchanged (mlp48 2.41 ms, scan64 1.40 ms either way). All probes 0 wrong after. Regressions: `tests/test_const_convert_narrow.py` (127 cases, pass with the host fold on and off). (Intrinsic-route elementwise max/min NaN handling: see the next bullet.)
- **Opt-in intrinsic route (`JAX_METALLIB_ENABLE_INTRINSIC_NATIVE_KERNELS=1`): elementwise max/min NaN and a constant-buffer pool defect.** The default route is unaffected by everything here (`build/probe_elementwise_minmax_nan.py` 0/168 before and after). (1) Fixed (`runtime/metal_kernels.mm` `nb_max`/`nb_min`): all 18 native elementwise `binary_{max,min}_{,vec4_,vec8_,stride_}{f32,f16}` kernels used Metal `max`/`min`, which return the non-NaN operand, at every size (n=17 included). They now test NaN on the bit pattern (the library uses default fast math) and return the NaN operand. Plain max/min cases in the probe: 24 wrong -> 0; whole intrinsic probe 101/168 -> 67/168. Regression: `tests/test_reduce_minmax_nan.py::test_intrinsic_elementwise_max_min_propagate_nan` (fails on the old kernels, passes now). (2) Not fixable outside `mps_executable.mm` (read-only here): fused elementwise chains (`maximum` next to add/sub/mul/min, `clip`, relu) are generated by `GenerateFusedKernelSource` from the `FusionSnippet` template `"max({in0}, {in1})"` / `"min(...)"`, which drops NaN; `JAX_METALLIB_DISABLE_ELEMENTWISE_FUSION=1` removes this class (intrinsic probe 67/168 -> NaN-mask failures 0). The fix is to emit a NaN-propagating helper (like `nb_max`) in that template. (3) Silent wrong results, not fixable outside `mps_executable.mm`: a native scalar `stablehlo.constant` step (intrinsic route only; `IsEligibleConstantScalarOp` admits f16/f32/i32/bool) binds its plan-owned `baked_constant_buffer` into `slot_bufs` with a `CFRetain`, and the end-of-run cleanup recycles every non-input, non-output, non-cached slot into the size-keyed `ReusableOutputPool`. The constant buffer therefore enters the pool while the plan still uses it; the next program that acquires that bucket overwrites it, and later runs of the first program read the other program's value. Reproduced for f16 (`build/probe_f16_sequence.py`: after running `clip(a, -0.5, 0.5)`, `maximum(a, 0.0)` computed `maximum(a, -0.5)`; 7 of 8 rounds wrong for several functions at n=4096 and 1M; round 0 always correct); f32 was clean in the same sequence (not proven safe, likely different bucket reuse). `JAX_METALLIB_DISABLE_OUTPUT_BUFFER_POOL=1` gives 0 wrong. The fix is to skip slots whose buffer is a step's `baked_constant_buffer` in that recycle loop (or release instead of recycle). Both (2) and (3) are further reasons the intrinsic family stays opt-in.
- **Known ±0 / NaN tie-break differences** (found by `build/probe_sort_edges.py`, 51 sort/top_k/argmax/select_and_scatter/scan edge cases; all others match CPU): (1) `lax.top_k` treats -0 and +0 as equal and keeps index order, where XLA puts +0 first. (2) `max`/`min` reductions over a slice containing only ±0 return the later zero, where XLA returns +0 for max and -0 for min. (3) max-pool gradients (`select_and_scatter` via MPSGraph `maxPooling2DGradient`) with a NaN inside a window send the gradient to the first maximum; XLA's sequential `ge` select lands on the first maximum after the last NaN, or on the NaN when it is the window's last element. Values are identical in all three; only the sign of a zero or the position that receives a gradient differs. Each fix would add a second full pass to every float top_k/max/min/max-pool gradient, so they are left as documented limitations.
- **Linalg lowerings live in Python** (`src/jax_plugins/silicon/linalg_lowerings.py`, registered for platform `mps` in `register()`): eigh/svd (Jacobi, real and complex, incl. SVD U/V without complex QR), complex triangular_solve/cholesky/geqrf/householder_product (real dtypes delegate to JAX's default rule, i.e. the native kernels), hessenberg/tridiagonal (LAPACK-packed, match CPU elementwise), Schur (complex: Hessenberg + Wilkinson-shifted QR, enables `sqrtm`; real: Francis double-shift QR + LAPACK dlanv2 standardisation of 2x2 blocks, enables real-input `funm`) and eig (from the complex Schur form, geev normalisation; real input with eigenvalues only, e.g. `jnp.linalg.eigvals`, reads the real Schur form's 1x1/2x2 blocks instead and skips the Schur vectors: n=32/64/128 0.5/2.1/8.4 s -> 0.10/0.41/1.59 s, rel. error vs LAPACK <= 4.6e-6, conjugate pairs adjacent with +imag first like dhseqr; real input with eigenvectors, e.g. `jnp.linalg.eig`, builds the complex Schur form from the real one with SciPy's rsf2csf Givens split instead of the complex QR iteration: n=32/64/128 0.53/2.11/8.76 s -> 0.11/0.46/1.71 s, rel. residual ~3e-8, eigenvalue error vs LAPACK <= 4.6e-6). `schur(sort_eig_vals=True)` raises `NotImplementedError` on MPS, as it does on XLA:CPU: JAX's own `_schur_cpu_lowering` refuses it ("The sort feature of LAPACK's gees routine is not implemented", jax/_src/lax/linalg.py:2250-2252 in the installed JAX) and the public `schur` docstring marks `sort_eig_vals`/`select_callable` as unused. This is an upstream JAX limitation, not an MPS gap; sorting only on MPS would diverge from the reference platform. Native-only `triangular_solve`/`cholesky` inside `case`/`while` bodies (e.g. `expm`, `polar`) use graph fallbacks registered with `REGISTER_NATIVE_MPS_OP_WITH_GRAPH_FALLBACK` (f16/f32, n <= 256).
- **`rng_bit_generator` lowered in Python** (`src/jax_plugins/silicon/random_lowerings.py`, registered for platform `mps`): the native handler (`random_ops.mm` `HandleRngBitGenerator`) ignored the input state, returned a zero state, rejected uint32 output ("UInt32 output is not supported") and aborted the process for uint8/uint16 (`MPSNDArray ... dimension length > INT_MAX`), so `jax.random` with `impl='rbg'`/`'unsafe_rbg'` was unusable on MPS. The lowering reimplements XLA's RngBitGeneratorExpander in uint32 lax ops (ThreeFry-2x32 and Philox-4x32; `RNG_DEFAULT` is Philox as on XLA:CPU), including XLA:CPU's narrow-ThreeFry split-axis/interleave layout and the u64[2] state update. Bits and returned state are bitwise equal to XLA:CPU for u8/u16/u32/u64, ranks 0-3, empty shapes, scan-threaded state and vmap (`build/probe_rbg_after_r19u.log` 26/26, `probe_rbg_shapes_after_r19u.log` 32/32). The key is routed through a gather before its words are extracted: when the key was not a direct graph argument (vmap's `keys[0]`, any sliced or computed key) MPSGraph spent > 60 s in `MemrefDeallocationPass` compiling the ThreeFry graph; with the gather it takes ~0.06 s (a masked-reduce key still hung, so the gather is the barrier, not any computed value). `jax.random.normal` differs from XLA:CPU by 1-2 ulp through the existing f32 `erf_inv` gap, independently of the generator (the default threefry PRNG shows the same). `JAX_METALLIB_DISABLE_RBG_LOWERING=1` restores the native handler. Regression: `tests/test_rng_bit_generator.py` (385 x32 + 129 x64 checks, ~17 s; aborts with the lowering disabled).
- **`a*b + c` vs XLA:CPU jit (f32, not a plugin bug)**: default MPS rounds the multiply and then the add, as StableHLO specifies, and is bitwise equal to NumPy two-rounding and to *eager* XLA:CPU. XLA:CPU *jit* contracts `a*b + c` (and `c + a*b`, and `a*b + c*d` as `fma(a, b, c*d)`) into an fma, but not `a*b - c` and not when `a*b` is also an output. On iid f32 data that is 15313/65536 elements (23%) differing from CPU jit (`build/probe_r20i_fma_who.log`). Treated as an upstream inconsistency; MPS is not changed to copy it. bf16 `a*b + c` differs from CPU (jit and eager agree) by the documented `JAX_METALLIB_BF16_STRICT_ROUNDING` trade-off; with the flag set all bf16 forms are bitwise equal (`build/probe_r20i_fma_who_strict.log`). The opt-in intrinsic route contracts both `a*b + c` and `a*b - c` (16261/65536 off CPU on `a*b - c`, all equal to fma; `build/probe_r20i_fma_contract.log`) and ran Adam at 2^24 2.6x slower than the default route (21.6-21.9 vs 8.3 ms; `build/probe_r20i_chain_real.log`, load ~3.3).
- **Long elementwise chains (perf, planner-side)**: one jit of 16 chained f32 elementwise ops at 2^24 costs 31-87 ms on default MPS vs ~1.8 ms on CPU; the same work as 4 jits of 4 ops costs 5-7 ms, and the opt-in intrinsic route fuses the runtime-operand chain in 1.84-1.88 ms (`build/probe_r20i_chain_split.log`). The plan is one graph segment at every length, and the cost past ~5-8 ops scales with bytes; `JAX_METALLIB_MPSGRAPH_OPT_LEVEL1` shows the same cliff. Realistic branched chains do not reach it: Adam, tanh-GELU and scale-shift-relu at 2^24 run 0.65-1.25x of CPU. A fix (splitting long single-output segments) belongs in `mps_executable.mm`.
